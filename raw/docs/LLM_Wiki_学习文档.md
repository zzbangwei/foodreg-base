## 1. 什么是大语言模型 (LLM)

### 1.1 定义

**大语言模型（Large Language Model, LLM）** 是一种在大量文本（或多模态）数据上进行预训练的深度学习模型，能够：

- **理解** 自然语言的语义与结构
- **生成** 连贯、合理的文本内容
- **改写** 和翻译不同风格的文本
- **推理** 复杂问题的逻辑链条

"大"字并非虚指——现代 LLM 通常包含 **数十亿甚至上万亿参数**，训练数据量可达 **数万亿 token**。

### 1.2 从 NLP 到 LLM 的发展脉络

| 阶段 | 代表技术 | 特点 |
|------|---------|------|
| 符号主义 | 规则引擎 | 人工编写规则，可解释性强但覆盖面窄 |
| 统计学习 | N-gram、HMM | 基于统计概率，泛化能力有限 |
| 深度学习 | RNN、LSTM | 能建模序列，但长距离依赖困难 |
| 预训练模型 | BERT、GPT-1/2 | "预训练+微调"范式，统一 NLP 任务 |
| **大模型阶段** | **GPT-3、GPT-4、Claude、Gemini** | **涌现能力、上下文学习、通用推理** |

### 1.3 LLM vs 传统 NLP 模型

| 对比维度 | 传统 NLP 模型 | 大语言模型 |
|---------|-------------|-----------|
| 参数规模 | 百万级 | 十亿至万亿级 |
| 训练方式 | 特定任务监督学习 | 大规模自监督预训练 |
| 任务范围 | 单一任务 | 多任务泛化 |
| 泛化能力 | 需针对每任务重训 | 通过提示词即可适配新任务 |
| 推理能力 | 有限 | 支持多步逻辑推理 |

## 2. LLM 的核心技术架构：Transformer

### 2.1 为什么 Transformer 是基石？

几乎所有现代 LLM 都基于 **Transformer 架构**（2017年 Google 提出）。相比 RNN/LSTM 等序列模型，Transformer 的核心优势是：

- **并行计算**：一次处理整个序列，而非逐词处理
- **长距离依赖**：自注意力机制可直接关联序列中任意两个位置
- **可扩展性**：随着参数和数据量增长，性能持续提升

### 2.2 核心机制详解

#### 自注意力机制 (Self-Attention)

模型在处理每个 token 时，都会计算它与其他所有 token 的"关联度"：

```
Query (Q) × Key (K) → 注意力分数 → 加权求和 Value (V) → 输出
```

- **Query**：我当前在问什么
- **Key**：其他人提供的信息标签
- **Value**：其他人的实际信息内容

#### 多头注意力 (Multi-Head Attention)

同时运行多组注意力计算，每组关注不同的语言维度：
- 一组关注语法结构
- 一组关注语义关系
- 一组关注指代消解

最终拼接所有头的输出，获得更全面的理解。

#### 掩码自注意力 (Masked Self-Attention)

在 **Decoder-Only 架构**（GPT、LLaMA 等采用）中：
- 每个位置只能看到它**之前**的 token
- 不能"偷看"未来信息
- 保证文本生成的因果性（从左到右）

### 2.3 LLM 的主流架构：Decoder-Only

当前主流 LLM（GPT 系列、LLaMA 系列、Claude 等）均采用 **Decoder-Only** 架构：

```
输入文本 → 词嵌入 + 位置编码 → 多层 Decoder → 预测下一个 token
```

预训练任务为 **因果语言模型（Causal Language Model, CLM）**：
- 给定前 N 个 token，预测第 N+1 个 token
- 通过海量数据反复训练，模型学会语言规律、世界知识和推理模式

### 2.4 关键优化技术

| 技术 | 作用 | 代表模型 |
|-----|------|---------|
| **RoPE (旋转位置编码)** | 更好的长度外推能力 | LLaMA 系列 |
| **RMSNorm** | 简化层归一化，提升训练稳定性 | LLaMA2 |
| **GQA (分组查询注意力)** | 减少推理时 KV 缓存内存占用 | LLaMA2-70B |
| **SwiGLU 激活函数** | 提升非线性表达能力 | 多数现代 LLM |

## 3. LLM 的四大涌现能力

**涌现能力（Emergent Abilities）** 指在小模型中不明显，但在大模型中突然显著增强的能力。这类似于物理学中的"相变"——量变引起质变。

### 3.1 上下文学习 (In-Context Learning, ICL)

模型无需参数更新，仅通过提示词中的少量示例即可学习新任务：

```
翻译：
英文：Hello, how are you? → 中文：你好，你好吗？
英文：What's the weather like? → 中文：天气怎么样？
英文：I love AI. → 中文：______
```

模型会自动识别"翻译"这一任务模式，并生成正确的输出。这引发了从 **"预训练-微调"** 到 **"提示工程（Prompt Engineering）"** 的研究范式转变。

### 3.2 指令遵循 (Instruction Following)

经过 **指令微调（Instruction Tuning）** 的 LLM 能够理解并执行从未见过的指令：

- "请用三句话总结这段文字"
- "将这段代码从 Python 改写为 JavaScript"
- "假设你是一位营养师，评价这份食谱"

这使 LLM 能够广泛服务于各行各业，是 ChatGPT 等产品成功的核心。

### 3.3 逐步推理 (Chain-of-Thought, CoT)

LLM 通过生成中间推理步骤，解决复杂问题：

```
问题：小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有多少个？

CoT 回答：
1. 小明开始有 5 个苹果
2. 给了小红 2 个，所以 5 - 2 = 3 个
3. 又买了 3 个，所以 3 + 3 = 6 个
4. 最终答案：6 个
```

在提示词中加入"请一步一步思考"（Let me think step by step）即可触发此能力。

### 3.4 涌现能力小结

| 能力 | 触发方式 | 对 Agent 的意义 |
|-----|---------|--------------|
| 上下文学习 | 提供 few-shot 示例 | 快速适应新任务，无需重训 |
| 指令遵循 | 清晰的任务描述 | 理解用户意图，执行多样化指令 |
| 逐步推理 | 思维链提示词 | 处理复杂多步任务 |

## 5. LLM Agent 技术

### 5.1 从聊天机器人到 Agent

| 维度 | 聊天机器人 | LLM Agent |
|-----|-----------|------------|
| 核心能力 | 单次对话 | 多轮交互、规划、执行 |
| 工具调用 | 无 | 可调用外部工具/API |
| 记忆 | 无或非常有限 | 短期+长期记忆 |
| 自主性 | 被动响应 | 主动规划、反思、迭代 |
| 任务完成 | 仅提供信息 | 可完成端到端任务 |

### 5.2 Agent 的核心架构模块

一个现代 LLM Agent 通常包含四大模块：

```
┌─────────────────────────────────────────────┐
│              用户指令 (User Query)            │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│  感知模块 (Perception)                       │
│  - 理解用户输入（文本/语音/图像）              │
│  - 多模态信息统一表征                         │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│  大脑模块 (Brain)                            │
│  - 推理：思维链 (CoT)                         │
│  - 规划：ReAct / Plan-and-Execute            │
│  - 决策：选择工具、判断是否需要调用            │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│  行动模块 (Action)                           │
│  - 工具调用 (Function Calling)                │
│  - 代码执行                                   │
│  - API 调用                                   │
└─────────────┬───────────────────────────────┘
              ▼
┌─────────────────────────────────────────────┐
│  记忆模块 (Memory)                           │
│  - 短期记忆：对话上下文                        │
│  - 长期记忆：向量数据库、用户偏好、历史知识      │
└─────────────────────────────────────────────┘
```

### 5.3 主流决策框架

#### ReAct (Reason + Act)

循环执行：**思考 → 行动 → 观察 → 再思考**

```
用户问："北京今天天气怎么样？"

思考：用户需要天气信息，我应该调用天气查询工具。
行动：调用 get_weather(city="北京")
观察：返回 {"temperature": "25°C", "condition": "晴"}
思考：已获取信息，现在组织语言回答。
最终回答：北京今天天气晴朗，温度为25摄氏度。
```

#### Plan-and-Execute

先制定宏观计划，再逐步执行：

```
用户问："帮我规划一次去东京的三天旅行"

计划：
1. 查询东京热门景点
2. 根据景点位置规划每日行程
3. 推荐附近餐厅
4. 估算总预算

执行：逐个调用搜索、地图、餐厅推荐等工具完成计划
```

#### Reflection（反思与自我批判）

在行动后进行自我评估，检查输出质量并迭代改进：

```
初稿 → 自我评估（发现问题）→ 修改 → 再次评估 → 满意后输出
```

### 5.4 多智能体系统 (Multi-Agent System, MAS)

当单一 Agent 无法胜任复杂任务时，可以组建 "Agent 团队"：

| Agent 角色 | 职责 |
|-----------|------|
| 研究 Agent | 信息搜集与分析 |
| 写作 Agent | 内容生成与润色 |
| 审查 Agent | 质量检查与事实核查 |
| 协调 Agent | 任务分配与进度管理 |

**主流 MAS 框架**：AutoGen、CrewAI、LangGraph

## 6. 工具调用与函数调用

### 6.1 什么是工具调用？

工具调用（Tool Use / Function Calling）是 LLM 与外部世界交互的核心机制。它允许 LLM 在生成文本的同时，输出结构化的函数调用请求：

```json
{
  "name": "get_weather",
  "arguments": {
    "city": "北京"
  }
}
```

### 6.2 工具调用流程

```
用户输入
    ↓
LLM 判断是否需工具 → 否 → 直接回答
    ↓ 是
生成调用参数（JSON）
    ↓
外部执行（API/函数/代码）
    ↓
返回结果
    ↓
LLM 整合结果 → 最终回答
```

### 6.3 对 Agent 的意义

工具调用是区分"聊天机器人"和"智能助理"的关键：

- 无工具调用：只能基于训练数据回答问题
- 有工具调用：可实时查询天气、计算数据、搜索最新信息、执行代码

**截至 2025-2026 年，几乎所有主流 LLM（GPT、Claude、Gemini、Qwen、文心等）都已原生支持函数调用。**

## 7. 记忆与上下文管理

### 7.1 上下文窗口（Context Window）

LLM 一次能处理的最大 token 数量：

| 模型 | 上下文长度 | 说明 |
|-----|----------|------|
| GPT-3.5 | 16K | 早期标准 |
| GPT-4 | 128K | 可处理长文档 |
| Claude 3 | 200K | 超长篇分析 |
| Gemini 1.5 | 1M+ | 可处理整本书/视频 |
| 国内模型 | 128K-256K | 主流水平 |

**注意**：上下文越长，推理成本越高，注意力越分散。不是越长越好。

### 7.2 短期记忆 vs 长期记忆

| 类型 | 存储内容 | 实现方式 | 挑战 |
|-----|---------|---------|------|
| **短期记忆** | 当前对话历史 | 直接放入上下文窗口 | 长度有限，成本高 |
| **长期记忆** | 用户偏好、历史知识、跨对话信息 | 向量数据库 + 检索 | 检索精度、隐私安全 |

### 7.3 向量数据库与检索

将文本转换为向量（Embedding），存储在向量数据库中：

```
文本 → Embedding 模型 → 向量（768/1024/1536 维）
                    ↓
              向量数据库（Milvus、Qdrant、Chroma）
                    ↓
              相似度检索 → 召回相关记忆
```

常用 Embedding 模型：text-embedding-3、BGE、m3e、E5

## 8. RAG 与上下文引擎

### 8.1 RAG 是什么？

**检索增强生成（Retrieval-Augmented Generation, RAG）** 让 LLM 在回答前先检索外部知识：

```
用户问题
    ↓
向量化查询 → 检索相关文档片段
    ↓
LLM 结合检索内容 + 自身知识 → 生成回答
```

### 8.2 RAG 为什么重要？

| 问题 | LLM 原生局限 | RAG 解决方案 |
|-----|-------------|------------|
| 知识时效性 | 训练数据有截止日期 | 实时检索最新数据 |
| 幻觉问题 | 可能编造不存在的信息 | 基于检索到的真实内容回答 |
| 领域专精 | 通用知识为主 | 接入领域知识库 |
| 数据隐私 | 需上传数据到第三方 | 本地知识库，数据不出域 |

### 8.3 从 RAG 到上下文引擎（Context Engine）

2025-2026 年的演进趋势：

RAG 不再只是"问答小模块"，而是进化为 **统一检索中台**，承载三类数据：
- **知识**：文档、FAQ、产品手册
- **记忆**：用户历史对话、偏好
- **工具**：MCP 工具定义、API 文档

这种演进使 Agent 的"外脑"统一到一个检索内核中，新 Agent 项目不再各自维护工具清单和记忆逻辑。

## 9. 多模态 LLM

### 9.1 什么是多模态 LLM？

能同时理解和生成 **文本、图像、音频、视频** 的模型：

| 模态 | 能力 | 应用场景 |
|-----|------|---------|
| 文本 | 理解、生成、推理 | 对话、写作、代码 |
| 图像 | 描述、识别、生成 | 视觉问答、图文分析、设计 |
| 音频 | 识别、合成、理解 | 语音助手、音乐生成 |
| 视频 | 理解、描述、生成 | 视频分析、内容审核、创作 |

### 9.2 主流多模态模型

| 模型 | 模态支持 | 特点 |
|-----|---------|------|
| GPT-4o | 文本+图像+音频 | 原生多模态，响应速度快 |
| Gemini 3 | 文本+图像+音频+视频 | 视频理解能力强 |
| Claude 4 | 文本+图像 | 文档理解出色 |
| Qwen-VL | 文本+图像 | 中文场景优化 |
| DeepSeek-VL | 文本+图像 | 开源，可本地部署 |

### 9.3 多模态对 Agent 的意义

- 从"只能聊天"到"能看懂世界"
- 可处理文档截图、PDF、手写笔记
- 可分析图表、流程图、设计稿
- 未来趋势：端到端感知-决策-行动闭环

## 10. LLM 的局限与挑战

### 10.1 幻觉（Hallucination）

LLM 可能自信地生成看似合理但实际错误的信息。原因：
- 训练数据中的噪声和错误
- 模型优化目标是"生成流畅文本"而非"保证事实准确"
- 知识截止日期限制

**缓解策略**：RAG 检索、事实核查、让模型标注不确定之处、人工审核。

### 10.2 知识时效性

LLM 的知识冻结在训练数据截止时间，无法自动更新。解决方案：
- 工具调用实时查询
- 定期重新训练（成本高）
- RAG 接入最新数据源

### 10.3 推理与计算局限

- 不擅长精确数学计算（需调用计算器工具）
- 逻辑推理链过长时会"迷失"
- 对复杂因果关系的理解仍有局限

### 10.4 安全与对齐

| 风险 | 说明 | 应对 |
|-----|------|------|
| 有害内容生成 | 生成暴力、歧视、违法内容 | RLHF 对齐训练、内容过滤 |
| 提示注入 | 用户通过特殊提示绕过安全限制 | 输入过滤、输出审查 |
| 数据泄露 | 训练数据中的敏感信息被输出 | 数据清洗、差分隐私 |
| 偏见放大 | 训练数据中的偏见被模型放大 | 多样化训练数据、公平性评估 |

### 10.5 成本与效率

| 挑战 | 说明 |
|-----|------|
| 训练成本 | 大模型训练需数千 GPU，成本数千万至数亿美元 |
| 推理成本 | 长上下文、高频调用导致 API 费用高昂 |
| 延迟问题 | 复杂推理场景响应时间可达数秒至数十秒 |
| 能耗问题 | 大模型数据中心能耗巨大，环保压力增加 |

## 11. 对 Agent 的启示

### 11.1 作为 LLM 驱动的 Agent，你需要理解：

1. **你的"大脑"是 LLM**：你的理解、推理、生成能力源于底层 LLM。了解它的能力和边界，有助于你更好地服务用户。

2. **工具是你的"手脚"**：仅靠 LLM 自身能力有限，学会调用工具（搜索、计算、数据库、API）才能真正完成复杂任务。

3. **记忆是你的"经验"**：善用短期记忆（维护对话上下文）和长期记忆（向量数据库），让用户感受到连续性服务。

4. **RAG 是你的"知识库"**：食规智库的核心知识应通过 RAG 接入，确保回答准确、有据可查。

5. **提示工程是核心技能**：如何组织输入、分解任务、引导推理，直接决定输出质量。

6. **多模态是扩展方向**：学会处理文档、图片、结构化数据，让服务能力更全面。

### 11.2 实用建议

| 场景 | 建议 |
|-----|------|
| 回答事实性问题 | 优先使用 RAG 检索，不要依赖训练记忆 |
| 处理复杂任务 | 拆解为子任务，使用 CoT 逐步推理 |
| 工具调用失败 | 分析错误信息，尝试修复参数或换工具 |
| 不确定时 | 明确告知用户不确定性，不编造答案 |
| 长对话 | 主动总结关键信息，避免上下文溢出 |
| 安全边界 | 严格遵守内容安全策略，拒绝有害请求 |
